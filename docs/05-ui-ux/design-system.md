0. نظام التصميم الأساسي (Design System Foundations)
قبل أي شاشة، يجب تجميد هذه الأسس لضمان اتساق بصري وسرعة تطوير عبر كل الفريق — هذا ما يحقق "واجهات سلسة ومريحة" و"خفيف وسريع" المطلوبين منذ بداية المشروع.

0.1 مبدأ التصميم المعماري: Atomic Design
text

Tokens (ألوان/مسافات/خطوط)
   └─ Atoms (زر، حقل إدخال، أيقونة)
        └─ Molecules (بطاقة حساب، صف قائمة)
             └─ Organisms (نموذج القالب الكامل، شريط التنقل)
                  └─ Templates (هيكل الشاشة العام)
                       └─ Pages (الشاشة الفعلية بالبيانات الحية)
السبب: يتيح بناء "عارض القوالب العام" (Generic Template Renderer) المذكور سابقًا دون كتابة شاشة منفصلة لكل زر — القالب يُركِّب نفس الـ Atoms والـ Molecules ديناميكيًا حسب تعريف JSON.

0.5 نظام الألوان الدلالي (Semantic Color Tokens)
لا ألوان حرفية في الكود — طبقة دلالية تتيح تبديل الثيم لاحقًا دون لمس الشاشات.

الرمز الدلالي	الاستخدام	مثال قيمة
color.positive	زيادة/ربح/تحصيل	أخضر #1E9E6B
color.negative	نقصان/خسارة/دين عليك	أحمر #D64545
color.neutral_info	معلومة محايدة	أزرق #2F6FED
color.warning	تنبيه (صلاحية قريبة، تجاوز ائتمان)	برتقالي #E8A33D
color.surface	خلفية البطاقات	أبيض/رمادي فاتح حسب الثيم
color.cash / color.bank / color.wallet	تمييز بصري لطرق الدفع الثلاث	ألوان متمايزة ثابتة
قاعدة إلزامية: أي مبلغ "يزيد" (مدين لحساب أصل، أو دائن لإيراد حسب القاعدة في renderSimpleSummary) يُلوَّن بـ positive، والعكس بـ negative — هذا يُترجم بصريًا فلسفة "التبسيط لغير المحاسب" مباشرة في الواجهة.

12. أنماط الحالات العامة (Universal State Patterns)
تُطبَّق هذه الأنماط عبر كل الشاشات دون استثناء لضمان اتساق تجربة المستخدم.

الحالة	المعالجة الموحّدة
تحميل	SkeletonLoader بنفس شكل المحتوى المتوقع (لا دائرة تحميل عامة)
قائمة فارغة	EmptyStateView برسم توضيحي بسيط + نص تشجيعي + زر إجراء مباشر ("أضف أول عميل")
خطأ شبكة	لا يظهر خطأ تقني؛ العملية تُحفَظ محليًا وتُعرض بحالة "بانتظار المزامنة"
تعارض مزامنة نادر	إشعار غير مزعج + شاشة مراجعة مبسّطة: "حدث تحديث من جهاز آخر، أيهما تعتمد؟"
نجاح عملية	اهتزاز خفيف (Haptic Feedback) + SimpleSummaryCard — لا نوافذ Alert تقليدية
صلاحية مرفوضة	إخفاء العنصر كليًا من الواجهة، لا عرضه معطّلًا (يقلل الإرباك لغير المختص)
13. الأداء المُدرَك (Perceived Performance) — ممارسات إلزامية
التقنية	التطبيق
Optimistic UI	عند الضغط "حفظ"، تنتقل الشاشة فورًا لـ"الملخص" قبل اكتمال الكتابة الفعلية في SQLite (تحدث خلال ملي ثوانٍ، لكن الإحساس يكون آنيًا)
تحميل مسبق للقوالب	كل ملفات templates/*.json تُحمَّل عند أول فتح للتطبيق وتُخزَّن محليًا، لا تُجلَب عند كل ضغطة زر
Debounce على البحث	ContactPickerSheet وItemPickerSheet تبحث محليًا (SQLite) أولًا، فورية بلا تأخير شبكة
تحديد عمق الشجرة المعروضة	accounts الهرمية تُحمَّل حتى مستويين فقط افتراضيًا في أي Picker، لا الشجرة الكاملة
صور وأيقونات متجهة (SVG/Icon Font)	لا صور Raster ثقيلة في الواجهة الأساسية، يحقق هدف حجم تطبيق < 30 ميجا
14. إمكانية الوصول (Accessibility) — لغير المختصين تحديدًا
المبدأ	التطبيق
تباين لوني كافٍ (WCAG AA)	خاصة بين color.positive/negative والخلفية
حجم خط قابل للتكبير	دعم textScaleFactor النظام دون كسر التخطيط (تجار بأعمار متقدمة)
أزرار كبيرة باستمرار	لا أيقونات صغيرة بلا نص توضيحي بجانبها في الشاشة الرئيسية
دعم قارئ الشاشة الأساسي	توصيف (semanticLabel) لكل حقل، رغم أن الفئة المستهدفة نادرًا ما تعتمد عليه، إلا أنه معيار جودة لا يُهمَل

القاعدة	الآلية
كل شاشة جديدة تُبنى من مكوّنات القسم 0.6 فقط، لا Widgets مخصصة متفرقة	مراجعة كود إلزامية (Code Review Checklist)
اختبار كل قالب عبر العارض الديناميكي دون كتابة اختبار UI منفصل لكل زر	Widget Test عام يُغذَّى بكل ملفات templates/*.json تكراريًا

اختبار RTL كامل (لا نص أو أيقونة معكوسة خطأ)	فحص بصري آلي + يدوي قبل كل إصدار
16. خلاصة وتوصيات
"عارض القالب الديناميكي" (القسم 3) هو الاستثمار الهندسي الأهم في طبقة الواجهة بأكملها — ابنِه وثبّته جيدًا قبل أي شاشة أخرى، فكل زر جديد مستقبلًا (من أي نشاط: عيادة، ورشة، محاماة) سيمر عبره دون كود إضافي.
لا تبدأ بشاشات التقارير الاحترافية (دفتر اليومية، ميزان المراجعة) في أول نسخة تُعرض على تاجر حقيقي — ابدأ اختباراته بالشاشات الخمس الأساسية: الرئيسية، عارض القالب، الملخص، جهات الاتصال، المخزون.
اختبر شاشة "الأمر الذكي" (القسم 11) مع مستخدمين حقيقيين مبكرًا جدًا — نجاح هذه الميزة بصريًا يعتمد كليًا على وضوح شاشة "التأكيد قبل الحفظ"، فهي خط الدفاع الوحيد ضد أخطاء فهم اللهجة.
التزم بمبدأ "لا نافذة Alert تقليدية" في كل التطبيق — استبدلها دومًا بمكوّنات مدمجة في التدفق الطبيعي للشاشة (كما في SimpleSummaryCard وEmptyStateView)، فهذا يرفع الإحساس بالجودة والسلاسة بشكل ملحوظ لدى غير المختصين.
راجع هذه الـ Wireframes مع 3-5 تجار حقيقيين فعليًا (ورقيًا أو بنموذج تفاعلي بسيط) قبل البرمجة — خاصة شاشة "عارض القالب" وحقل اختيار العميل/المورد، فهما الأكثر استخدامًا والأكثر حساسية لأي ارتباك.
بهذا اكتملت الوحدات الخمس الأساسية: المحاسبة، المخزون، الذمم، التقارير، والواجهات. الخطوة المنطقية المتبقية من النقاش السابق هي تصميم وحدة الاشتراكات والدفع عبر المحافظ الإلكترونية اليمنية — هل ننتقل إليها؟
